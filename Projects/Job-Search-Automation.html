Project

Job Search Automation

The challenge

After being made redundant, I was looking at multiple role types across several job boards. Finding roles by hand was repetitive, the same role often turned up in more than one search, and it was hard to judge quickly which ones deserved a tailored application. I saw a chance to answer two questions at once: could I turn this into a working system, and could I build real, hands-on skills in AI automation while doing it?

My role

I set this up as a self-directed proof of concept. I defined the eight search profiles, the scoring approach, the 60% threshold and the salary and location filters, then built and tested the workflow in n8n myself. Once the concept was proven, I prepared it for public release, including the data-protection review, the README and the pipeline diagram.

What I built

A scheduled workflow in n8n that ran the front end of the search from start to finish:

Claude was given my CVs, an outline of my experience and background, and an achievement tracker. It compared each job description against all of this and returned a match percentage.

Find:
Searched eight role profiles in parallel on Welcome to the Jungle using Apify scrapers.
Clean:
Merged the results into one list, removed duplicates and filtered against my target salary and location.
Score:
A fast, low-cost AI model (Claude Haiku) rgave each role its match percentage
Gate:
Roles with a match below 60% were logged and skipped so they were never processed again. Roles at 60% or above moved on.
Write:
A more capable model (Claude Sonnet) assessed each qualifying role in detail and drafted a tailored cover letter straight into Google Docs.
Log:
Results went to Google Sheets, on separate tabs for applications, processed roles and rejections.

Using a single, capable model for everything worked, but it was expensive. Splitting the work let a cheap model handle the high-volume triage and kept the expensive model for the few roles where the writing had to be good.

Outcome

Concept proven:
The full pipeline ran from start to finish, from searching to a drafted cover letter, with no manual steps in between.
Design validated:
The two-tier approach brought AI costs under control. Threshold gating and deduplication removed duplicated effort, and the costlier model was used only on roles that qualified.
Skills gained:
Practical experience of workflow orchestration, API integration, AI model selection and prompt design.
Lasting asset:
Published as a public GitHub repository with a README, a pipeline diagram and setup steps, so others can adapt it. The workflow is no longer running, but it would work again with fresh credentials.

What I learned

AI costs more than you think:
The first iteration of the pipeline did not differentiate between roles and models and watching the token usage was possibly as close as I'll get to understanding Cameron in Ferris Bueller's Day Off
Start with a clear goal and an MVP:
I built the pipeline over several iterations, each with a specific job to do. The first version was deliberately narrow: one role profile and one job board, finding roles and scoring them. Once that worked reliably, I added logging, then more role profiles, then the rest. A clear goal kept each iteration focused and told me when the whole thing was finished. Building from an MVP meant problems showed up early and cheaply, the token costs being the obvious example, instead of being buried in a finished system.
Filter early, spend late:
Do the cheap checks (dedupe, salary, location, first-pass score) before anything expensive. This applies to project delivery as much as to AI.
Use the right model for each job:
Matching the tool to the stakes keeps costs down without lowering quality where it counts.
A threshold is a judgement call:
Set it too high and you miss good roles; set it too low and the gate stops doing anything.
Sanitise before you publish:
Sensitive data ending up in public repositories is an increasingly common problem as AI speeds up how quickly code is written and shared. Before publishing, I removed my contact details, target salary, private document IDs and instance references, checked the result, then published. A manual check is still essential, however the code was written.
