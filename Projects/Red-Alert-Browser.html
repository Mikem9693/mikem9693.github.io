Project

Red Alert in Browser

The challenge

Command & Conquer: Red Alert is currently available on a browser however this uses DOS emulation running noticably slower, freezing and stuttering on modern machines. The games source code is available under the GPL presening a solution. Complining the oroginal engine for the web. The code written in the early 90s presents a challenge as it assumes it controls the whole machine. Resulting in hanging loops and attemopted interaction with hardware unavailable on web pages

My role

I am running this as a Product owner/delivery lead, with an AI coding assistant (Claude Code) as the engineer. I scope the work into tickets with clear acceptance criteria, set the gates each phase must pass, review every change before it’s committed, and decide what’s in or out of scope. Alongside the delivery, I’m learning the technical side hands-on: the Linux toolchain, C++ build systems and WebAssembly.

What I am building

A browser version of Red Alert built from the open-source Vanilla Conquer engine, compiled to WebAssembly with Emscripten:

Currently with the release of Fable 5.2 Anthopic are alloing Fable usage as part of a pro subscription with a usage reset availabe before 18th Novmeber 2026 (6 days from starting the project) The aim is to utilise the more powerful Fable model whilst usage is available at no cost

  • Skirmish and campaign play in desktop Chrome, Edge and Firefox, from a single link
  • Players load their own legally obtained game files; no copyrighted game data is hosted
  • A clean, documented fork with each change scoped and explained, structured so that improvements could be offered back to the original open-source project
  • Online multiplayer planned as a second phase

Using a single, capable model for everything worked, but it was expensive. Splitting the work let a cheap model handle the high-volume triage and kept the expensive model for the few roles where the writing had to be good.

Intended Outcome

  • A version that runs smoothly where emulation struggles, backed by a recorded side-by-side performance comparison rather than impressions
  • Measured delivery data: planned against actual effort per phase, AI usage and cost, and defects caught at review
  • A working example of how to direct AI on real engineering work safely: clear briefs, small changes, evidence-based review

Vanilla Conquer is the original repo I built from

What I'm Learning

Managing AI delivery:
writing tickets an AI can execute well, using plan-first workflows, reviewing diffs instead of trusting output, and matching model and cost to task difficulty
Delivery discipline with AI:
phase gates, change control when an assumption proves wrong, isolating variables when diagnosing problems, regression testing and structuring development to stay within usage limits
Technical foundations:
Linux and WSL, Git workflows, CMake and C++ builds, WebAssembly and the browser event loop
Responsible open source:
GPL obligations, keeping copyrighted assets out of public code, and the etiquette of contributing upstream
Agentic AI
Instructing Fable 5.2 to create and manage Opus 5.5 agents to undertake bulk of coding work whilst Fable acts as a 'conductor'. This approach reduced token usage and allowed more to be completed within budget
