Project

Network Wide Adblocker

The challenge

Ads, trackers and background telemetry were reaching every device in my home. Browser extensions only protect the one browser they’re installed in. I wanted a single filtering layer for phones, laptops, a gaming PC and everything else, without installing software on each device.

My role

Sole designer, builder and administrator. I chose the hardware (a Raspberry Pi 4B), installed and configured Pi-hole, set up the router, and handled the troubleshooting, updates and monitoring.

What I built

A DNS-level filtering service on a Raspberry Pi that sits in front of every device on my home network, with extra layers around it to cover what DNS alone can’t.

Adverts are becoming more and more frequent even on paid platforms. This project was a great opportunity to impliment a fix whilst developing a new skill

Host:
A Raspberry Pi 4B on a wired connection, with a reserved address on the router so the rest of the network can always find it.
Install:
Installed Pi-hole, chose Cloudflare as the upstream resolver and added the OISD blocklist, taking the lists to around 300,000 domains. When the first install left the blocklist database missing, I rebuilt it from the command line.
Score:
Pointed the router’s DHCP settings at the Pi so every device uses it automatically. I kept Cloudflare as a fallback, so the network still works if the Pi is switched off.
Route:
Roles with a match below 60% were logged and skipped so they were never processed again. Roles at 60% or above moved on.
Layer:
Added uBlock Origin Lite in the browsers to handle page-level ads that DNS can’t see. This also addressed structural issues of page layouts pulling blank space where adverts previously existed
Close the gaps:
Worked through the ways devices were quietly bypassing Pi-hole, including encrypted DNS in Chrome and Edge and Apple’s Private Relay.
Monitor
Used the dashboard and query log to check each device, spot noisy apps and tell real blocking from one app retrying in a loop. I also kept the system and Pi-hole updated and enabled SSH for remote administration.

implementing DNS level ad blocking worked well but website were still showing where adverts previously existed so the user experience was less than perfect

Outcome

Concept proven:
A working Pi-hole serving around six devices, with a reserved IP address, an expanded blocklist, SSH access for remote administration and up-to-date software.
Design validated:
Tracker and telemetry traffic blocked across phones, laptops and apps, not just in browsers.
Skills gained:
Several bypasses found through the query log and closed, including browser encrypted DNS and a weak ad blocker on one laptop.
Lasting asset:
A hardware fault recovered after moving the Pi (an SD card that had come loose).

Find this automation and instructions on the Pi-hole GitHub

What I learned

DNS filtering is one layer, not a complete answer:
It works best alongside a browser-level blocker, and some ads need neither.
Dashboard headline numbers can mislead:
One app accounted for most of the blocks on some days, comparison with per-device and per-domain data will quickly give you a clear answer.
Most problems were bypasses:
As most things slipping through the net were not blocklist gaps. The first question should always be whether the device is asking Pi-hole at all.
Very quickly, projects are no longer hobbies
As with everything, once people become acustomed to a standard going back is not an option. My partner who questioned the value of this project was the first to ask why she was seeing adverts and I was straight into troubleshooting

A level of compromise is needed especially in a shared home - This meant a small amount of adverts getting through to avoid creating a system that would require manual intervention for any and every issue

Next Steps

Moving beyond the home network
The natural next step is to expand beyond the current limitations of being connected to my home network. This would allow me to enjoy the beneifts of adblocking and tracking limitations whereever I find myself
Challenges
The usual fix of a VPN back into the home network requires an open port on my router.My provider shares one public address between customers, so an open port would never be reachable from outside.
I currently run a commercial VPN on my phone, its unliekly I would be able to run a second at the same time

Solutions Considered

Taiscales
This would only require outbound connections and therefore need no port forwarding and be feasible with the IPS restrcitions
Requesting a static IP address
This would cost around £5 a month and allow a conventional home VPN to be implemented. WireGuard server on the Pi and a single port forwarded on the router. It is the most direct technical fix, but it adds a monthly cost and an open port that I would need to keep patched. This ties back to creating solution that others in the house would be unlikely to fix in the case of an error
WireGuard relay on a rented Cloud Server
This would avoid my provider's restrictions without paying for a static address, but I would still add a cost and trusting a third party with the connection.

The only realistic option would be to utilise Taiscales, the other options very much enter the territory of over engineering and would reault in a much more fragile network removing the ease of use which we all expect
